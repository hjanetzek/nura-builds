# zynthian hardware on Nura: Raspberry Pi kits (plan)

Status: plan, 2026-11-10. Nothing built yet. First target: the **V4 kit on a Raspberry Pi 4**, with
one set of packages for all kits, as ZynthianOS has one image for all of them.

## What ZynthianOS does (zynthianos-last-stable.img, inspected 2026-11-10)

- **Kernel**: Raspberry Pi's own (Raspberry Pi OS, `6.18.50+rpt-rpi-v8` for the Pi 4,
  `-rpi-2712` for the Pi 5), stock firmware and device-tree overlays, `CONFIG_PREEMPT=y`
  (fully preemptible, not PREEMPT_RT), `HZ=250`. No zynthian overlays: kits use the stock ones.
- **Boot config** (`/boot/firmware/config.txt`, generated by zynthian-sys'
  `update_zynthian_sys.sh` from `boot/config.txt` and the kit's envars): for every kit
  `dtparam=i2c_arm=on`, `i2s=on`, `spi=on`, `dtoverlay=i2s-mmap`, `enable_uart=1` with
  `midi-uart0` (MIDI on the UART at 31250 baud), `miniuart-bt` on the Pi 4, `dwc2` (USB gadget),
  `vc4-kms-v3d`, `core_freq=500` on the Pi 4 (SPI clock of the RGB LEDs); per kit
  `#SOUNDCARD_CONFIG#` and `#DISPLAY_CONFIG#` (overlays) and the display's kernel options in
  `cmdline.txt` (`video=DSI-1:800x480@60,panel_orientation=upside_down` for the V5).
- **The kit** is chosen by `ZYNTHIAN_KIT_VERSION` and the envars file of zynthian-sys
  (`config/zynthian_envars_<kit>.sh`: wiring layout, I2C addresses and interrupt pins, sound card,
  display, switch actions); `sbin/zynthian_autoconfig.py` detects the kit by scanning I2C.
- **zyncoder** (encoders, switches, LEDs, ADCs, headphone amps) uses **wiringPi** (GPIO, I2C, and its
  MCP23017 extension), and the wiring layout, addresses and pins are **compile-time** `#define`s
  (CMakeLists.txt reads `ZYNTHIAN_WIRING_*` from the environment): ZynthianOS rebuilds zyncoder on
  the device whenever the kit config changes.
- zynthian runs as root with jackd.

V4 kit (`zynthian_envars_V4.sh`): wiring layout `MCP23017_ZynScreen` (MCP23017 interrupts on GPIO
2 and 7), sound card HifiBerry DAC+ ADC PRO (`dtoverlay=hifiberry-dacplusadcpro`), display
"ZynScreen 3.5 (v1)": 480x320 SPI panel, `dtoverlay=piscreen2r-notouch,rotate=270` and the ads7846
touch controller.

## Plan

### 1. Kernel: Alpine's linux-rpi, later an RT variant

pmaports' `raspberry-pi4` device uses Alpine's `linux-rpi` (6.18.60: mainline with Raspberry Pi's
patches, Raspberry Pi's `bcm2711_defconfig` plus Alpine's changes) and `raspberrypi-bootloader`
(firmware, `config.txt` that includes `usercfg.txt`). That is the same kernel family and config
as ZynthianOS', with the same overlays, kept up to date by Alpine: use it as is first.

**RT**: PREEMPT_RT is in mainline for arm64 since 6.12, so `linux-rpi-rt` can be Alpine's recipe
with `CONFIG_PREEMPT_RT=y` added to its `common-changes.config` (no patch set), providing
`linux-rpi` for the device package. Built in CI like the plugins; compared with the PREEMPT kernel
on the device (xruns at small buffer sizes, the Raspberry Pi drivers under RT). ZynthianOS itself
doesn't use RT.

### 2. Device package: `device-zynthian-rpi`

A pmaports device in nura-builds (`aports/device/device-zynthian-rpi`), from
`device-raspberry-pi4`: the same kernel and firmware, deviceinfo for the Pi 4 (the Pi 5 later: own
kernel flavour `bcm2712`), and a `usercfg.txt` with ZynthianOS' common settings (I2C, I2S, SPI,
i2s-mmap, the MIDI UART, miniuart-bt, dwc2, core_freq) and `include zynthian-kit.txt`: the kit's
overlays (sound card, display), written by step 4. Kernel command line from the kit too
(`deviceinfo_kernel_cmdline` plus the kit's display options, through pmOS' cmdline.txt generation).

### 3. zyncoder for the hardware: `zyncoder-hw` (started 2026-11-10)

One package with **one build of libzyncore.so per wiring layout** (the per-kit builds,
`/usr/lib/zynthian/hw/<LAYOUT>/libzyncore.so`), against Alpine's `wiringpi` (community):
`MCP23017_ZynScreen` (V4) first, then `V5`, `Z2_V3`, `MINI_V2`, `V5_ZYNFACE`, the other MCP23017
layouts with the addresses and pins of zynthian-sys' wiring profiles. zynthian-ui already loads
libzyncore.so from `ZYNTHIAN_LIB_DIR` (zyncoder's port commit): the launcher sets it to the layout's
directory when `ZYNTHIAN_WIRING_LAYOUT` names one, else the generic build (without GPIO) stays.
Custom wiring with other addresses: a layout build from the user's values later (or making zyncoder
read them at run time, upstreamable, as a second step).

### 4. Kit selection: `zynthian-hw`

The hardware glue from zynthian-sys, as a package (depends on `zyncoder-hw`, `wiringpi`, `i2c-tools`):
- `zynthian-kit` command: `zynthian-kit V4` (or `auto`: zynthian_autoconfig.py's I2C detection)
  writes the kit's envars to `/etc/default/zynthian` (from zynthian-sys-config's
  `zynthian_envars_<kit>.sh`), the overlays to `/boot/zynthian-kit.txt`, the display options to the
  kernel command line, and asks for a reboot when those changed.
- udev rules and groups: `/dev/gpiomem`, `/dev/i2c-*`, `/dev/spidev*` for the zynthian user (it
  runs as the session user, not root), realtime limits for the audio group.
- The ZynthianOS services that matter on the kits: backlight, the PWM fan
  (`zynthian-pwm-fan.py`), the RV3028 RTC; later.

### 5. Display: DRM for the SPI panels

The ZynScreen 3.5's overlay (`piscreen2r`) uses fbtft (`ilitek,ili9486` with fbtft properties:
`bgr`, `fps`, `rotate`): a framebuffer device only, no DRM, and cage (Wayland) and the Qt UI need
DRM. ZynthianOS uses X11 on that framebuffer. The kernel's tiny DRM driver `ili9486` supports the
OzzMaker PiScreen (`ozzmaker,piscreen`), which `piscreen2r` suggests the panel is based on: an
overlay of our own binding that driver (same SPI pins, DC/reset GPIOs, rotation), checked on the
kit. The V5's DSI panel and HDMI screens are DRM already.

**How to drive the 480x320 SPI panel** (to measure on the V4 kit): a full frame over SPI takes tens
of milliseconds (about 15-30 fps), a fullscreen copy in memory (600 KB at 32 bit) well under one:
what counts is how much goes over SPI (partial updates of the changed regions: fbtft's deferred I/O
by pages, the DRM driver by damage rectangles), not one copy more or less. The Pi 4's GPU (V3D) can
still render through its render node; only the copy to the panel's buffer is the CPU's.

| Option | Display server | Panel driver | Notes |
|---|---|---|---|
| A. framebuffer, as ZynthianOS | Xorg, fbdev driver | fbtft (`piscreen2r`, /dev/fb1) | Tk UI natively; the Qt UI through xcb |
| B. X11 on DRM | Xorg, modesetting driver (no glamor) | DRM `ili9486` (own overlay) | the same for the UIs, damage to the panel through DRM |
| C. Wayland kiosk | cage | DRM `ili9486` | as on the Duet; the Tk UI through XWayland (one X server and compositor more) |
| D. no display server | none: Qt's `linuxfb` | fbtft or DRM (dumb buffer) | Qt UI only, the lightest; no plugin GUIs (jalv's GTK windows need a display server) |

**Measured, option A** (2026-11-10, ZynthianOS as installed on the user's V4-type kit: Raspbian 10,
32-bit kernel 5.15.70-v7l, fbtft at 64 MHz with deferred I/O at 33 fps, Xorg fbdev, the Tk UI;
zynthian-ui's `nura/tools/display_bench.sh`, which counts the bytes the SPI controller sends to the
panel):

| | Panel traffic | Full frames/s | CPU (one core) |
|---|---|---|---|
| Panel limit (fbtft, UI stopped, full frames written) | 39.3 MB in 6.8 s | 16.7-18.8 | |
| UI idle (main menu) | 1.36 MB/s | 4.4 | |
| UI scrolling a list (5 steps/s) | 2.18 MB/s | 7.1 | Xorg 0.9 %, UI 8.0 % |

The idle UI keeps the panel a quarter busy: fbtft sends the full rows of every changed page
(the top bar's CPU meter and clock), not the changed rectangle. A DRM driver sends the damage
rectangles: options B to D should send much less at idle.

Measure per option: frames per second of the panel at a full redraw and while scrolling a list
(the UI's switch timing tools), CPU load of the UI and the display server/compositor
(`nura/tools/thread_cpu.sh`), input latency of the touch panel, and xruns under audio load.

### 6. Image

nura-builds' zynthian target gets the device (DEVICES `zynthian-rpi`): the kiosk image with
`zynthian-hw`; the kit chosen at first boot (`zynthian-kit auto`) or in the admin menu.

## Findings on the Pi 4 (2026-11-10)

Nura on the user's V4-type kit (Pi 4 2 GB, HifiBerry DAC+ ADC non-Pro, ZynScreen 3.5, MCP23017 at
0x20 with interrupts on GPIO 27/4; Zynaptik-2 at 0x21/0x48/0x60 unused). Hardware data: the user's
`~/bastel/cynthian/port/hal/zynthian_v4/HARDWARE.md` and `dumps/` (read from ZynthianOS).

Setup: stock pmbootstrap image (`~/.config/pmbootstrap-zynthian-rpi4.cfg`: device raspberry-pi4,
UI console, hostname zynthian-rpi4, user jeff), the nura-builds repository and key added, the kiosk
(postmarketos-ui-zynthian) from it; device-zynthian-rpi4, zyncoder-hw, zynthian-hw built locally
(`nura/deploy.sh -c ~/.config/pmbootstrap-zynthian-rpi4.cfg -H zynthian-rpi4.local -u jeff ...`;
the device recipe from the branch `merge-device`, linked into the local pmaports as
`device/nura-builds`). The device swap: `apk add device-zynthian-rpi4.apk '!device-raspberry-pi4'
'!device-raspberry-pi4-udev'` (one transaction: linux-rpi and the firmware stay).

What works: linux-rpi 6.18.58 boots with our usercfg.txt; HifiBerry DAC+ADC; the MCP23017 through
zyncoder-hw (`MCP23017_ZynScreen`, wiringPi 3.16): zyncore sets up 8 switches and 4 encoders and
the interrupts fire (counted in /proc/interrupts); ads7846 touch; the panel through fbtft
(`piscreen2r,rotate=270`); the Qt UI on Qt's linuxfb (option D) **runs surprisingly well**, but
needs another theme for 480x320.

Problems found and fixed:
- zyncoder-hw had no wiringPi: a `case $CARCH` added wiringpi-dev to makedepends, which
  pmbootstrap reads statically: the kit builds used zyncoder's stand-in (no GPIO/I2C). Now its own
  recipe (zynthian-ui `nura/zyncoder-hw`), failing if a build lacks libwiringPi.
- No /dev/i2c-1: i2c-dev wasn't loaded. The device package loads it now (modules-load.d, r3). With
  the real wiringPi a missing I2C device *exits* zynthian (the stand-in only failed).
- zynthian-kit created zynthian_envars.sh before the first start: the launcher's setup was skipped
  (no midi-profiles: the UI crashed). It runs zynthian's setup now.
- Output scale 1.5 (the Duet's) on the Pi: the kiosk session uses 1 on Raspberry Pis (r22).
- Touch flipped on both axes (as on ZynthianOS, where X has a calibration matrix): libinput needs
  `LIBINPUT_CALIBRATION_MATRIX="-1 0 1 0 -1 1"` for the ADS7846 (a udev rule; Qt's evdev rotate
  parameter is ignored, Qt uses libinput). On the Pi as /etc/udev/rules.d/91-zynscreen-touch.rules;
  still to add to the device package.

Open:
- **DRM ili9486 (zynscreen-drm overlay)**: the driver binds (card, /dev/dri/zynscreen, backlight on,
  cage runs on it, SPI traffic flows) but the panel stays white, at 64 and 32 MHz: its init
  sequence (the original PiScreen / Waveshare 3.5") doesn't suit this panel revision; piscreen2r's
  sequence (in the cynthian dumps) differs (power control, 0xB6 display function control, ...).
  Needs the ili9486 driver with that sequence (the panel's 16-bit bus interface rules out the
  generic panel-mipi-dbi). Until then: fbtft, so no cage (options B, C).
- **Encoders and switches do nothing in the Qt UI**: the hardware events arrive, but the Qt UI has
  no hardware input loop (TODO in `~/bastel/github/zynthian-stuff/TODO.md`; another agent takes it).
- **The on-screen keypad** gets its actions only with touch navigation
  (`ZYNTHIAN_UI_TOUCH_NAVIGATION=v5_keypad_left/right`: wiring-profiles/v5 and 24 virtual switches,
  zynthian_gui_config.py); the V4 kit turns it off, the Custom kit has it (keypad works).
- The kiosk on fbtft: cage needs DRM; option D runs zynthian outside the kiosk for now: a user
  service (`systemd-run --user --unit=zynthian-linuxfb -E QT_QPA_PLATFORM=linuxfb:fb=/dev/fb0:nographicsmodeswitch
  -E QT_QPA_FB_HIDECURSOR=1 -E ZYNTHIAN_UI=qt -E ZYNTHIAN_FULLSCREEN=1 /usr/bin/zynthian`), with
  `loginctl enable-linger jeff` (else the user's systemd, PipeWire with it, stops with the last SSH
  login), fbcon unbound from fb0 (`echo 0 > /sys/class/vtconsole/vtcon1/bind`: the blinking cursor),
  jeff in video and input. A kiosk mode for linuxfb (and the X11 option A) would make it a session.
- The device-zynthian-rpi4 commits (device, setup.sh link, zynthian-hw and zyncoder-hw in the
  zynthian stage) are on the nura-builds branch `merge-device`, not yet in main (pushed after the
  running Qt rebuild).

**Measured, option D** (Qt UI, Qt linuxfb on fbtft, Nura): idle 0.03 MB/s (0.09 full frames/s),
scrolling 0.62 MB/s (2.0 frames/s), UI 19 % CPU. Option C (cage on DRM, panel white but traffic
measurable): idle 1.07 MB/s, scrolling 1.98 MB/s, UI 26 %, cage 0.9 %. Without a compositor Qt
flushes only the changed rectangles, and fbtft sends only those pages. (Not the same screens:
C on the Add Chain menu, D on the mixer; Tk against Qt for A.)

## Order

1. `zyncoder-hw` with the V4 layout, built in CI (wiringpi, musl).
2. `device-zynthian-rpi` and an image for the Pi 4 (kernel linux-rpi): boots, sound through the
   HifiBerry (PipeWire), I2C and GPIO visible.
3. `zynthian-hw` (`zynthian-kit V4`), permissions; encoders and switches in zynthian.
4. The ZynScreen 3.5 as DRM (overlay), touch.
5. `linux-rpi-rt`, compared on the device.
6. More layouts (V5 on Pi 5 needs the bcm2712 kernel), autodetection, fan, RTC.
